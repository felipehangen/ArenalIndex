# Purchase offers — November 11, 2026

## Current design: inviting property welcome and buyer proposal

The user requested a minimalist reusable form, with sharing only from the listing list and a more considered buyer experience. This supersedes the original five-step design documented below.

- Each published listing has **Formulario de oferta / Offer form**. Clicking it opens a native modal with **Copy link** and **View form**, retaining the current Listings tab, search, and scroll position. The same reusable link serves every buyer for that listing. There is no private reference or per-buyer setup.
- Offers is an inbox only: received proposals, search, refresh, review status and historical copies. No link-creation button or property selector remains there.
- The sharing popup names the property, supports loading/error/retry and manual copy when the clipboard is denied. Close, Escape and backdrop dismissal restore focus. Separate request generations prevent closed popups, newer selections and expired sessions from receiving stale data.
- The buyer starts on a property welcome screen: an arched cover photo, property name, location, size, asking price and receiving broker. **Prepare my offer** explains that the buyer reviews before sending to the named broker. The cover opens a swipeable, keyboard-accessible gallery with the listing’s published images. No generated property photography is used.
- **View full listing** opens the actual catalog detail in the same tab. The listing has **Back to offer** before a draft exists and **Continue my offer** afterward, including its Back control and mobile footer. Only the matching property gets these controls. Welcome, draft and review state, typed entries, contact preference, focus and writing position are retained locally. `sessionStorage` is primary; browser history state carries the same journey when it is blocked. Tokens and draft contents are never added to public listing URLs or analytics.
- **Ask … on WhatsApp** prepares only a property-specific question using the published contact number. It opens WhatsApp without sending. If a listing names a separate public contact, that name is used; the offer’s receiving account remains explicit. No private account contact details or fallback numbers are exposed.
- The draft is one page: amount/currency, optional conditions or note, name, then **How would you like the broker to reply?** WhatsApp and Email sit side by side; only the selected field is visible and required. WhatsApp has an international country-code selector, a custom-code option and a phone keypad. International numbers pasted with `+` are not prefixed twice. The unselected contact stays in the local draft and is excluded from submission. There are no financing, deposit, closing-date or expiry questions.
- **Review my offer → Send to [broker]** turns the inputs into an editable paper-style proposal. Only the explicit final Send writes a submission. The confirmation says **You’ve taken the first step**, followed by **We’re rooting for you — The ArenalIndex team** (Spanish: **Ya diste el primer paso / Estamos con vos**). It preserves the exact submitted proposal and private printable copy. Reduced motion disables animation; print styling isolates the proposal.
- Shared links use `#listing.<id>.<signature>` and only return current published property information and broker name. Each submission becomes a separate private record. The shared link never returns buyer details or earlier offers.
- The buyer receives a separate `#receipt.<id>.<signature>` URL, placed in the browser address after sending, plus a printable copy. Receipts can be read only with their own capability or from the authenticated broker inbox. The shared form cannot be used to access them.
- Forms remain usable while the listing is published and assigned to the active account. Removing the listing or suspending the account stops new offers. Revoking one receipt does not disable the shared form or other receipts.
- `server/offers/simple.mjs` adds `offer_form` (account), `offer_form_open`, `offer_form_submit`, and `offer_receipt` (capability access). `server/offers/links.mjs` separates listing/receipt token purposes. Private form metadata lives in `portal/offer-forms/`; submissions reuse the account’s existing private offer index. No new environment variables or database migration.
- Submissions recheck the current property snapshot, validate the short form and record exact notice/language/time. Stable submission identifiers prevent duplicates after lost responses. If an earlier attempt already saved different terms, the response returns the saved receipt with an explicit explanation instead of overwriting it.
- The shared property snapshot now includes only published gallery URLs and the public WhatsApp contact. Schema 2 adds optional `replyMethod` metadata with server-side contact consistency validation; older submissions without it remain valid and readable. No new secrets or migration are required.
- Older private links accept the short form; all prior submissions and full-form terms remain readable. Earlier unused links are available under the account’s “Earlier links” filter. They are never converted into shared links.

390 tests pass, including shared-link privacy, separate receipts, listing/modal isolation, gallery arrows/swipes, same-tab listing return, storage-blocked recovery, selected-channel validation, international number normalization, draft position restoration and the complete bilingual review/send interaction. Build passes. Visual browser QA remains unavailable: automatic approval review blocked inspection because local browser use remains disabled. Release through the existing Vercel API and GitHub Pages workflow.

## Original design (historical)

The account has an **Ofertas / Offers** tab next to My listings and Resources. Published listing rows offer **Invitar a ofertar / Invite a buyer**. The account creates one private invitation per buyer, optionally with an internal reference. The buyer needs no account.

The bilingual form uses the existing green/white interface, a property summary, five short steps (amount, purchase plan, conditions, buyer details, review), tab-scoped draft saving, and explicit confirmation naming the broker. Buyers can request guidance on financing and deposit terms. Price and deposit preserve the chosen USD/CRC currency; no automatic conversion occurs. The asking-price snapshot is identified as the price when invited. Demo properties are explicitly marked and request test data.

Submission records the buyer's proposed terms for discussion, not a purchase agreement, reservation, seller acceptance, payment or signature. The exact explanatory notice, language, server submission time, proposed validity and immutable revision are retained. No claim of identity verification or attorney review is made.

## Account and buyer behavior

- Account inbox shows invitations, received offers, review status and search. Opening Offers or Refresh loads new submissions. No automatic email is sent; the buyer confirmation says so explicitly.
- Copying a link only copies it. Sending it to a customer remains the broker's action.
- Buyer links use the `/offer/#...` fragment, keeping the capability out of normal server request URLs and referrers. Anyone holding the private link can view the proposal and submit revisions, as both interfaces explain.
- Invitations permit submission for 30 days. An expired invitation preserves access to its submitted copy until the broker closes the link. Closing a link prevents buyer reads/writes and preserves the account's records.
- The buyer can submit revised terms; up to 20 immutable versions remain visible. Review status is internal and does not communicate acceptance.
- Buyers and brokers can print/save the displayed latest proposal as PDF through the browser. Long conditions can span multiple pages. Prior versions are visible on screen and excluded from the default printout.
- Form drafts are stored in sessionStorage for that tab only, with a fallback notice when storage is blocked. Successful submission clears that draft.

## Implementation and access

`server/offers/core.mjs` provides account actions and unauthenticated capability actions through the existing `/api/owner` endpoint. Account actions reuse Google/password sessions, activation, temporary-password and listing-rule checks. Creation accepts only currently published properties assigned to the account (including assigned demos). Submission rechecks current ownership/publication and account activation. Public responses explicitly omit private listing records, documents, owner subjects, account email and internal invitation references.

Invitations are private Blob records in `portal/offers/`; per-account indexes under `portal/offer-index/` support pagination and filter ownership again during reads. HMAC capabilities reuse the existing review secret with a dedicated purpose string. No new environment variables or SQL migration are needed. CORS, request bounds, input validation, per-IP rate limits and conditional ETag writes apply. Creation and submission use stable request identifiers to recover retries without duplicating records. Stale revisions cannot overwrite newer proposals.

Frontend: `site/offer/`, `site/cuenta/offers.mjs`, and small integrations with the account and shared listing controller/view. Vercel includes the new modules and marks the form route private/no-store/noindex. No analytics are loaded on the buyer form.
