# Two-broker pilot

## User-confirmed plan

All listings present on November 22, 2026 are demos. Felipe and one broker friend will use the platform themselves and aim to add 20–30 real listings by December 31, 2026. Broader broker onboarding will be considered after a period of real use. No subscription price, billing threshold, referral-fee model or additional broker recruitment has been decided.

Keep existing demos as demonstrations. Create distinct new records for actual properties rather than turning demonstration records into real inventory. Existing demo metadata survives edits and re-publication. A real listing requires accurate property information, owner authorization, suitable photographs, reviewed public contact and the normal approval/publication checks. “Documented” means the record distinguishes seller statements from reviewed material; it is not a legal or engineering guarantee.

## Learning during the pilot

For each genuine listing, work through save, preview, submit, review, publish, share, receive an offer, update and withdraw as those actions become relevant. Note actual friction and questions from buyers. Keep listings current and avoid duplicate records for the same property. The useful signals are completed/current listings, repeat use by the two brokers, buyer questions, and follow-up outcomes—not raw WhatsApp clicks.

After using the platform, decide whether seller reports, a small lead log or carefully qualified asking-price comparisons would solve repeated problems. Do not build billing around anonymous analytics. Plan indexable canonical pages and a sitemap for genuine listings as real inventory arrives; demos and private offer pages should not be promoted as actual property search results.

## Technical preparation

- Public catalog, collection HTML, and social previews: CDN cache of 30 seconds; browser revalidation; no stale extension. Error responses are uncached.
- Published photo endpoint: checks current publication/photo/version, then serves a prepared JPEG with a five-minute browser/CDN cache. Private files remain private, with unchanged signed access. Originals remain retained. Future publication rejects media without a bounded generated JPEG derivative.
- Public collection slugs use their existing reservation and account keys instead of reading every account. Legacy opaque account links keep the compatibility lookup. Missing/stale slug reservations cannot fall back to an unrelated account.
- The release command tests and deploys an isolated committed snapshot. Vercel also runs the tests in its build. Pages requires the matching public runtime fingerprint from both API hosts before publishing, including scheduled runs. PRs run tests without deploying.
- The README now describes current account, publication, offer and release behavior. The old README is archived; dated notes remain linked historical evidence.

Public withdrawal semantics are explicit: origin rejects new access immediately, public text can remain cached up to 30 seconds and JPEGs up to five minutes. A previously issued legacy signed URL can remain valid up to ten minutes. Downloaded files and third-party social previews cannot be recalled.

## Deployment integration limitation

The existing Vercel CLI account can deploy, but the attempt to connect `felipehangen/ArenalIndex` through Vercel's Git integration failed. Browser project settings require sign-in. Automatic Git-triggered Vercel deployment is therefore not claimed as configured. The release command and Pages fingerprint check prevent accidental frontend/API mismatch without adding a long-lived Vercel token to GitHub. Continue using the release command until a Git integration and its source marker have been configured and verified together.

The runtime digest includes frontend/API/server source, dependency manifests, Vercel configuration, and build helpers. It excludes documentation, Pages-only metadata, tests and the changing exchange-rate snapshot. The release marker contains only this digest. Vercel rewrites `vercel.json` during the build, so the release command captures the committed input as `release-source-config.json` in its isolated upload and the cloud fingerprint reads that copy. The local/CI fingerprint always reads the source `vercel.json`. Keep these inputs complete when adding a new runtime/build directory.

## Next stages

Measure public latency and storage operations with real pilot use before choosing a larger data migration. A Postgres migration remains a reasonable direction for querying records and aggregating analytics, but no migration or new paid service is part of this preparation. Broader formatting/module extraction and a CSP rollout should be incremental changes with regression checks, not a wholesale rewrite during the pilot.
